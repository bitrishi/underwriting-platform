How Neo4j Stores Data Physically

Key Concept: Index-Free Adjacency
Each node has a direct physical pointer to its relationships. Each relationship has pointers to its start/end nodes AND the next relationship. Traversal = following pointers. No index scan needed after finding the starting node.

Node Record (fixed 15 bytes)

Node: John Doe (ID: 4200)
in_use: true
first_rel: → REL#8100
first_prop: → PROP#AA00
labels: [:Borrower]

// Position = 4200 × 15 = byte 63000
// Finding this node: instant (just math)
Node: TechCorp (ID: 6044)
in_use: true
first_rel: → REL#8100
first_prop: → PROP#BB00
labels: [:Company]

Relationship Record (fixed 34 bytes)

Relationship: WORKS_AT (ID: 8100)
start_node: → NODE#4200 (John)
end_node: → NODE#6044 (TechCorp)
type: WORKS_AT
start_next_rel: → REL#8200 (John's next rel)
start_prev_rel: NULL
end_next_rel: → REL#8150 (TechCorp's next rel)
end_prev_rel: NULL
first_prop: → PROP#CC00 ({since: 2019})
Doubly-Linked List of Relationships
Each relationship has start_next_rel and end_next_rel pointers. This forms a doubly-linked list around EACH node.

John's relationships: WORKS_AT → APPLIED_FOR → FRIENDS_WITH → NULL
TechCorp's relationships: WORKS_AT(John) → WORKS_AT(Jane) → IN_INDUSTRY → NULL

Finding ALL of John's relationships: follow the chain. O(k) where k = number of John's relationships. NOT affected by total database size.

Property Records (linked list per node)

PROP#AA00 (John's first prop)
key: "name"
value: "John Doe"
next: → PROP#AA20
PROP#AA20
key: "fico"
value: 740
next: → PROP#AA40
PROP#AA40
key: "income"
value: 120000
next: NULL

Indexes in Neo4j

Indexes: Only for Finding the Starting Node
MySQL: Indexes needed for EVERY query. Without index → full table scan.
Neo4j: Index needed ONLY to find the entry point. After that, traversal is index-free.

CREATE INDEX FOR (b:Borrower) ON (b.ssn_last4)

Step 1: Find John via index → needs index (B-tree lookup)
Step 2: John → WORKS_AT → TechCorp → no index (follow pointer)
Step 3: TechCorp → IN_INDUSTRY → Technology → no index (follow pointer)
Step 4: Technology → HAS_RISK → {default_rate: 3.2%} → no index (follow pointer)

Graph Traversal vs SQL JOIN

Query: "Find the industry default rate for John's employer"

MySQL Approach (Index Scans)

1
Scan persons index → find id=1 (John)
O(log n)
2
Scan employment index → find person_id=1
O(log n)
3
Read company_id=5 from row
O(1)
4
Scan companies index → find id=5
O(log n)
5
Scan company_industries index → find company_id=5
O(log n)
6
Scan industries index → find id → read default_rate
O(log n)
Total: 5 index scans
Cost: O(5 × log n) — grows with table size
1M rows: ~100 comparisons per scan
With 8 JOINs on large tables: can take seconds

Neo4j Approach (Pointer Following)

1
Index lookup: find John by SSN
O(log n)
2
Follow pointer → WORKS_AT relationship
O(1)
3
Follow pointer → TechCorp node
O(1)
4
Follow pointer → IN_INDUSTRY relationship
O(1)
5
Follow pointer → Technology node → read default_rate
O(1)
Total: 1 index scan + 4 pointer follows
Cost: O(log n + 4) — only first step grows with size
1M nodes or 1B nodes: same traversal speed
Pointer follow = direct memory access = nanoseconds

Relationship Patterns

One-to-Many: Company → Employees
TechCorp has 3 employees. Each WORKS_AT relationship is a separate record in the relationship store. They form a linked list hanging off TechCorp's node.

TechCorp.first_rel → rel1(John) → rel2(Jane) → rel3(Bob) → NULL

Finding all employees: follow the chain. O(3) — constant per relationship, not affected by total DB size.
Bidirectional: Stored Once, Traversed Both Ways
(John) -[:WORKS_AT]→ (TechCorp)

Stored as ONE relationship record with both start_node and end_node pointers.

Forward: MATCH (john)-[:WORKS_AT]->(company) — follows start→end
Backward: MATCH (company)<-[:WORKS_AT]-(person) — follows end→start
Either: MATCH (john)-[:WORKS_AT]-(x) — no arrow = both directions

One record, two traversal directions. No duplication needed.
Cyclic: Naturally Supported
(Company A) -[:SUBSIDIARY_OF]→ (Company B) -[:SUBSIDIARY_OF]→ (Company C) -[:OWNS]→ (Company A)

Each relationship is an independent record. Cycles are just more relationship records — no special handling needed.

Cypher prevents infinite loops with path length limits:
MATCH path = (a)-[:SUBSIDIARY_OF*1..5]->(b)
*1..5 = follow 1 to 5 hops maximum. Auto-avoids revisiting nodes.
Relationships Can Have Properties Too
(John) -[:WORKS_AT {since: 2019, position: "Senior Eng", salary: 120000}]→ (TechCorp)

The relationship record has its own property chain (linked list), just like nodes. Useful for storing metadata about the connection itself — when it started, the role, etc.

When to Use What

Question Type Best Store Why
"Get loan APP-001 details" MongoDB / SQL Simple document lookup — CRUD
"List all loans this month" MongoDB / SQL Filter + aggregate on structured records
"What does the DTI regulation say?" Vector DB (FAISS) Semantic search over document content
"What industry is John's employer in?" Graph DB (Neo4j) 2-hop relationship traversal
"What's the default rate for John's industry?" Graph DB (Neo4j) 3-hop traversal: borrower → employer → industry → risk
"Find similar past loans with outcomes" Graph DB (Neo4j) Multi-hop pattern matching across entities
"Is this borrower connected to flagged entities?" Graph DB (Neo4j) Fraud network — variable depth traversal
"What regulations apply to this Texas loan?" Graph + Vector Graph finds regulations, Vector gets full text

Your Underwriting System Architecture

Polyglot Persistence — Right Store for Right Job
MongoDB (DocumentDB) — Primary store. All CRUD, UI, reports. Loan documents, borrower profiles, amendments, payments.

Neo4j — AI knowledge graph. Relationship traversal for risk context, similar loans, regulatory mapping. Read-only, synced from MongoDB.

FAISS / OpenSearch — Vector store. Semantic search over policy documents. RAG retrieval.

Redis — Caching. Session data, frequently accessed records.

PostgreSQL — Analytics. Complex aggregations via Glue ETL.

You already do this in Camelot (DocumentDB + Redis + PostgreSQL). Adding Neo4j for AI agents is the same pattern.
DON'T Replace MongoDB with Graph DB
MongoDB is perfect for Camelot's CRUD operations. Graph DB would make simple queries harder. Add Neo4j alongside as a secondary read-only store for AI agent use cases only. Sync selectively — only entities and relationships (~10% of data).
