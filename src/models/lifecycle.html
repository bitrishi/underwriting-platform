The Redeployment Problem: What Happens If You Change Code?

This is a CRITICAL production concern you identified. Let's walk through the scenarios.

Scenario: Loan APP-001 is paused at human_review. Before the human responds, you deploy new code.

⚠️ What the checkpoint stores: DATA, not CODE

The Redis checkpoint contains the state dictionary — the outputs of each agent as data (JSON blobs). It does NOT contain the agent code, the prompts, the tools, or the graph structure. Those live in your deployed code.

When you resume, LangGraph loads the STATE from Redis but uses the CURRENT CODE to continue execution.

✅ SAFE Changes (resume works fine)

  • Update prompts: Only affects agents that haven't run yet. For APP-001, fetch_data/doc_review/risk_scoring/compliance already ran. Only human_review and final_decision use the new prompts. Since these nodes don't call LLMs with system prompts (human_review just formats, final_decision just reports), prompt changes are safe.
  • Change scoring criteria: risk_scoring already ran with the OLD criteria. The score (46) is in the checkpoint as DATA. New criteria affect only NEW evaluations, not resumed ones.
  • Add logging/monitoring: No state impact.
  • Update tool implementations: Tools already called won't re-run. Only tools in nodes after the resume point are affected.
  • Change API response format: Only affects the FastAPI layer, not the graph state.

❌ BREAKING Changes (resume may fail)

  • Change state TypedDict fields: If you rename "risk_assessment" to "risk_result", the checkpoint has "risk_assessment" but the new code reads "risk_result". KeyError on resume. FIX: Add migration logic or keep old field names.
  • Remove a node that already ran: If you remove compliance_node, the checkpoint says compliance completed but the new graph doesn't have that node. LangGraph may error. FIX: Don't remove nodes while checkpoints exist for old graph versions.
  • Change graph topology: If you reorder nodes or change edges, the checkpoint's execution history doesn't match the new graph structure. FIX: Drain pending reviews before deploying topology changes.
  • Change Pydantic model fields: If the checkpoint contains a risk_assessment serialized with the old model and the new model expects different fields, deserialization fails. FIX: Version your models or add backward compatibility.

Production Deployment Strategy

The "Drain and Deploy" Pattern

  1. Before deploying breaking changes: Check for interrupted pipelines (pending human reviews)
  2. Option A — Drain: Notify reviewers to complete pending reviews before deployment. Deploy only when the pending queue is empty.
  3. Option B — Version: Tag each checkpoint with the code version that created it. On resume, if the checkpoint version doesn't match current code version, either (a) complete with the old code path or (b) restart the evaluation with new code.
  4. Option C — Backward compatible changes only: Never rename state fields. Never remove nodes. Only ADD new fields with defaults. Only ADD new nodes. This is the safest but most constraining approach.

What Goldman/Camelot Already Does

This is the same problem you have with Camelot's amendment workflows. If a loan amendment is in-progress (partially completed by a user) and you deploy new code that changes the amendment flow, the in-progress amendment might break.

Your existing solutions apply: blue-green deployment (old code handles old requests, new code handles new ones), database migrations with backward compatibility, feature flags to gradually enable new behavior.

For LangGraph: add a "graph_version" field to your state. On resume, check if the checkpoint's graph_version matches the current version. If not, decide: complete with backward-compatible logic, or restart the evaluation.

Your Questions Answered

Q: What does the user enter initially?

The underwriter in Camelot UI enters the application ID (e.g., APP-001) and uploads documents (W-2, pay stubs). They click "Evaluate." That's it. The API creates the initial state and starts the graph. The user doesn't know about thread_ids, checkpoints, or LangGraph — they just see a status update: "Evaluating..." → "Pending Senior Review" → "Approved with Conditions."

Q: Is the whole state configured/restored on resume?

Yes, completely. The checkpoint in Redis contains the FULL state — every field populated by every agent that ran. When LangGraph resumes, it deserializes this JSON into the same Python TypedDict structure. The in-memory state after resume is IDENTICAL to what it was at the moment of interrupt. It's like loading a save game — the entire world state is restored.

Q: What if I redeploy between interrupt and resume?

The checkpoint stores DATA (state values), not CODE (agent logic, prompts, graph structure). On resume, the restored data flows through the CURRENT code. Safe changes: prompt updates, scoring criteria changes, tool implementation updates, model swaps — because agents that already ran won't re-run. Breaking changes: renaming state fields, removing nodes, changing graph topology — because the checkpoint references the old structure. Solution: "drain and deploy" (complete pending reviews before breaking changes) or version your checkpoints.

Q: What if I add a new agent between interrupt and resume?

If you add fraud_check between compliance and human_review: the checkpoint says the next node is human_review. The new graph has fraud_check before human_review. LangGraph will try to resume at human_review and may skip fraud_check entirely (it wasn't in the graph when the checkpoint was created). Solution: make the new node optional (check if its output exists in state, skip if not) or drain pending reviews before deploying the new node.

Q: How does the response come back from API to agent?

The human submits via POST /api/reviews/APP-001/decision. Your FastAPI code calls graph_app.invoke(Command(resume="APPROVE_WITH_CONDITIONS..."), config={"configurable": {"thread_id": "APP-001"}}). LangGraph loads the checkpoint, sees it's interrupted at human_review, injects the resume string as the return value of interrupt(), and the node continues. The final result flows back through the graph to END, returns to your FastAPI code, which sends HTTP 200 to the UI.

Q: How does LangGraph know this is a resume vs a new evaluation?

The Command(resume=...) object tells LangGraph this is a resume, not a new invocation. A new evaluation passes a dict (initial_state). A resume passes a Command. LangGraph checks the type: if it's a Command with resume, it loads the checkpoint for the thread_id and continues. If it's a dict, it starts fresh.

Q: What if the Fargate task that started the evaluation is gone?

Doesn't matter. The checkpoint is in Redis, not in the Fargate task's memory. ANY Fargate task running the same code can resume. The resume call can come from a completely different server, different container, different availability zone. This is the entire point of externalizing state — your compute is stateless, your state is in Redis.
