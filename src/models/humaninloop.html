Key Points in the Diagram

  • checkpoint#1 through #6 — State is saved to Redis AFTER each node completes. If the process crashes between any two nodes, it resumes from the last checkpoint.
  • INTERRUPT — The state machine literally stops. The Python process can exit. Nothing is running. State lives in Redis.
  • RESUME — A new process (possibly on a different server) loads state from Redis and continues from the interrupt point.
  • The conditional edge (needs_manual_review?) is a Python function, not an LLM call. Zero cost, deterministic.

Your Questions Answered

Q: Does every checkpoint store the WHOLE context?

Yes. Each checkpoint is a complete snapshot. Checkpoint #3 (after risk_scoring) contains EVERYTHING from fetch_data, doc_review, AND risk_scoring. It is self-contained — you can resume from checkpoint #3 without needing checkpoints #1 or #2.

This is intentional. If checkpoint #3 only stored the DELTA (just risk_scoring's output), then resuming would require loading and replaying checkpoints #1, #2, and #3 in sequence. That is slower and more fragile. Full snapshots mean instant resume from any point.

The tradeoff is storage: each checkpoint duplicates earlier data. But at ~10 KB per checkpoint, this is negligible. Storage is cheap; resume speed and reliability are valuable.

Q: If I need to run the whole flow again, do I store ALL context of ALL agents?

If you restart from scratch: No stored context needed. You invoke the graph with fresh initial state (just app_id and document_paths). Each node runs and builds up state from nothing.

If you resume from a failure: The checkpoint has everything. Load checkpoint, continue from the failed node. Previous nodes' outputs are in the checkpoint.

If you resume from human review: The checkpoint has all 4 agents' outputs. Load it, inject the human's decision, continue to final_decision. No agent re-runs.

Q: The interrupt pauses the state machine — can you show a workflow diagram?

See Tab 1 for the state machine diagram with the interrupt point marked.

See Tab 3 for the step-by-step lifecycle showing exactly when the pause happens, what gets saved, and how resume works.

The key insight: the interrupt is NOT a sleeping thread or a waiting process. The state machine literally STOPS. The process exits. State is persisted externally (Redis). A completely new process can resume it later.

Q: When the human returns, how does LangGraph know this is a response and find the right chain?

The thread_id is the key. Here is the exact mechanism:

  1. On interrupt: Your API stores the thread_id (e.g., "APP-001") alongside the interrupt message. Your database knows: thread_id "APP-001" is pending human review.
  2. Human responds: The human submits their decision through your UI/API. Your API knows this is for thread_id "APP-001" because the review was linked to that thread_id.
  3. On resume: Your API calls app.invoke(Command(resume="human's decision"), config={"configurable": {"thread_id": "APP-001"}})
  4. LangGraph sees thread_id "APP-001" → looks it up in the checkpoint store (Redis) → finds the interrupted checkpoint → loads the full state → knows execution was paused at human_review_node → injects the resume value as the return of interrupt() → continues execution.

LangGraph does NOT "understand" that this is a human response. It simply sees: "thread APP-001 has a checkpoint in interrupted state. The caller provided a resume value. Inject that value and continue." The semantic meaning (human review) is YOUR application logic. LangGraph just handles the pause/persist/resume mechanics.

Q: What is the thread_id exactly?

It is a string YOU choose. For your underwriting system, use the application ID: "APP-001", "APP-002", etc. It serves the same purpose as a Step Functions execution ARN — uniquely identifies one pipeline execution.

Multiple concurrent evaluations each have their own thread_id and their own checkpoint chain. They do not interfere with each other.

Q: What if two processes try to resume the same thread_id?

The checkpoint store should use optimistic locking. When Process A loads the checkpoint to resume, it notes the checkpoint version. When it tries to write the next checkpoint, it checks the version hasn't changed. If Process B already resumed and advanced the checkpoint, Process A's write fails and it knows to abort.

In practice, your API should ensure only one resume call per thread_id. The pending review queue in Camelot UI should show "APP-001: pending review" and once a reviewer claims it, others see "APP-001: under review by Jane Smith."
